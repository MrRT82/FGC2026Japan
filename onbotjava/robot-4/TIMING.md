# 4号機のセンサー取得時間計測

計測は独立した `MainClass_Blue_Timing`（グループ `1_DIAG`）だけで行う。通常の `MainClass_Blue` / `MainClass_Red` と依存クラスは計測前のコミット `d482df9` の22ファイルと完全一致する。計測版は依存クラスを含めて `org.firstinspires.ftc.teamcode.timing` に分離した。通常版に計測の時計読取り・集計・分岐・追加CSV列はない。センサー取得頻度、順番、制御ゲイン、モーター指令は変更しない。計測用にセンサーを余分に読まない。

## 記録と使い方

- 計測版は `/sdcard/FIRST/logs/robot_blue_timing_日時.csv` に記録し、末尾に `tm_` 列がある。通常版のログは従来どおり `robot_日時.csv`。
- ビルド表示に `robot4_blue_timing_v2` が含まれることを確認する。
- 計測開始は前後スティックによる主要動作開始時。初期化時の読み取りは集計しない。
- 通常走行、射撃位置合わせ、発射操作中を分け、同じ条件を複数回記録して比較する。無理に詰まらせる必要はない。
- 終了は通常のSTOPを使い、CSV保存が完了してから取り出す。実機操作はユーザーの明示指示を受けて行う。
- `python tools/analyze_timing.py <CSVのパス>` で項目別の平均・最大・回数・例外と、モード別処理時間を表示できる。
- ログはGitHubへ追加しない。今回のPC上でのコンパイルは、Hub上のビルド・実機検証とは別である。

## 通常版との比較と配置

- Driver Stationでは通常Blue、通常Red、Blue計測版の3つのメインOpModeを選べる。計測版もBlueと同じ機構を操作するため、実行には通常の実機運転と同じ準備が必要。
- 通常Blueと計測Blueで同じ操作条件を比較する。通常版の既存 `period_ms`, `period_max`, `ovr_pct`, `ph_log` と、計測版の追加項目を併せて評価する。
- 計測版の依存クラスを複製しているため、通常版の機能変更は自動同期しない。比較の前に両版の制御内容が揃っているか確認する。
- `src` 以下の通常22ファイルと計測専用21ファイルの計43ファイルが今回のリポジトリ上の配布対象。Hubにある他の診断ソースは削除しない。
- `python -B tests/test_opmode_isolation.py` で通常22ファイルの完全一致、計測依存先の隔離、3つのメインOpMode登録名を検査する。

## 列の意味

各 `tm_<項目>` に次の4列がある。50ms間隔のログ行の間に完了した複数回の呼出しを集約し、間引かれた周期の遅い取得も最大値に残す。

| 接尾辞 | 意味 |
|---|---|
| `_n` | 前回出力以降の呼出し回数 |
| `_total_us` | 呼出し所要時間の合計（マイクロ秒） |
| `_max_us` | 1回の最大所要時間（マイクロ秒） |
| `_errors` | 例外が発生した呼出し回数（既存の例外処理は維持） |

平均msは `total_us / n / 1000`。`n=0` は未取得であり、ゼロ時間の測定ではない。複数行をまとめる場合も、合計時間÷合計回数で平均を出す。

| 項目 | 対象 |
|---|---|
| `imu_ypr`, `imu_gyro` | IMUの姿勢・角速度API。現在ジャイロ直読みは無効なのでgyroは通常0回 |
| `distance` | 測距API。別スレッド上の時間 |
| `velocity_shooter`, `velocity_drive`, `velocity_intake` | 機構別の速度API。左右および呼出し元を合算 |
| `pot_angle` | ポテンショ電圧・最大電圧の取得と従来どおりの角度換算 |
| `touch` | 登坂下端スイッチ。従来の短絡評価を維持 |
| `diag_*` | ロガーの電流・電圧取得。左右モーターを個別に計測 |
| `ff_voltage` | シューター補償用電圧。キャッシュヒットは計測しない |
| `optional_current` | 現在無効の追加電流制限・バランス用取得 |
| `cache_clear` | キャッシュ無効化処理。バルク通信そのものの時間ではない |
| `loop_period` | ループ先頭から次の先頭まで。周期調整の待機を含む |
| `loop_work` | ループ先頭から周期調整待機前まで。ログ処理も含む |
| `loop_overrun` | 期限を超過した回数と超過時間。ループ全体の時間ではない |
| `work_manual`, `work_shoot`, `work_fire`, `work_climb`, `work_discharge` | 終了時のモードで分類したloop_work。fireは射撃モードでRBを押している状態であり、実際にボールが出た証明ではない |
| `log_build` | 既存CSV本文の組立。途中のセンサーAPI取得を含む |
| `log_write`, `log_flush` | CSVバッファ書込みと定期flushを別計測 |

`dst_age_ms` は距離測定完了からの経過時間（未取得は-1）、`dst_reader_errors` は測距スレッドの累積例外数、`dst_reader_running` はスレッドの生存状態である。停止中の測距は生存していても読取りを行わない場合がある。鮮度はセンサー内部の測定時刻を保証しない。

## 解釈上の注意

- 所要時間は `System.nanoTime()` の実経過時間。API内部の待機、通信ロック待ち、OSのスケジューリングも含む。物理センサーの測定時間だけではない。
- SDKバルクキャッシュを維持しているため、速度などの最初の読み取りに通信時間が集中し、後続はキャッシュ参照になることがある。速度APIの回数は通信回数ではない。
- 距離スレッドと主制御は並行して動くため、`distance` を主制御の各時間に足してループ時間を求めてはいけない。Hub通信競合の有無は、測距の有無による比較試験で確認する。
- CSV列の集計窓は各カウンタの出力時点まで。現在のCSVの書込み・flush・当該ループの終了時間は、次のログ行に入る。モード切替付近は複数モードのセンサー取得が混ざるため、安定したモード区間で比較する。
- `log_build` はセンサー取得を内包し、`loop_work` はログ処理等を内包する。これらも二重加算しない。
- 通常終了直前の未出力の集計窓、および保存失敗時のデータは残らない場合がある。ログ末尾だけで判断しない。
- 生の全サンプルは保存しないので、厳密な95パーセンタイルや単一ループとの完全な対応は復元できない。平均・最大・回数による原因の絞り込みが目的。
- 計測にも時計読取り・集計・CSV列追加の負荷がある。主因を絞った後は取得頻度を変更した比較測定を行い、制御精度とデータ鮮度も確認して対策を決める。
